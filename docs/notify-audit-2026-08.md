# 자동문자·데이터 일관성 전수 점검 (2026-08-30)

8월 28일 '지난 배송' 문자 121건 오발송 이후, 손님에게 나가는 자동문자 전 경로와
화면 간 데이터 일치를 실데이터로 다시 훑었다. 아래는 찾은 것과 고친 것이다.

점검 범위: 앱 발송 12종 · 크론 3종 · 웹훅 2종, 그리고 구독 일정의 SQL·TS 이중 구현.
데이터 기준일 2026-08-30, 기간 최근 90일.

---

## 1. 정상 확인된 것

| 항목 | 결과 |
|---|---|
| 구독 배송일 계산: SQL(`sub_delivery_dates`) vs 앱(`computeSchedule`) | 활성 슬롯 73개 전부 일치 (0건 불일치) |
| 출고했는데 발송안내 문자가 안 나간 건 | 0건 |
| 문자 발송 실패 기록 | 0건 |
| 8/28 이후 '지난 배송' 문자 재발 | 0건 (서버 차단 작동 중) |

배송일 계산이 두 곳에 따로 구현돼 있는데도 값이 갈리지 않는다는 점은 확인해 둘 만하다.
전 슬롯의 1~24회차 날짜를 하나씩 맞춰 본 결과 어긋난 날짜가 없었다.

## 2. 찾은 결함

### ① 비회원 주문은 주문접수·입금안내 문자를 한 통도 못 받았다 — 20건
`lib/notify.ts` 의 발송은 로그인 세션 토큰으로 인증한다. 비회원은 세션이 없어
`/api/notify` 를 아예 타지 못하고, 코드도 `if (user)` 로 명시적으로 건너뛰고 있었다.

7/1~8/29 비회원 주문 20건 전부 미발송. 그중 SY20260829-9912(8/29 15:16 주문)는
안내 문자 없이 다음 날 아침 **입금 독촉(D1)부터** 받았다. 손님이 받은 첫 문자가 독촉이었다.

→ 고침: 전용 라우트 `POST /api/notify/guest` 신설. 수신번호·문구·중복방지를 전부 서버가
DB 권위값으로 판정하고, 비회원·입금대기·주문 30분 이내·주문당 1회로 범위를 좁혔다.
선물 주문은 보내지 않는다(받는 분 번호로 결제 안내가 갈 수 있어서).

### ② 자동 입금확인에는 입금확인 문자가 없었다 — 69건 중 65건 미수신
PayAction 웹훅이 입금을 자동 매칭하면 주문 상태만 바뀌고 문자는 나가지 않았다.
관리자가 화면에서 직접 '입금확인'을 누른 건에서만 문자가 나간다.

7/1 이후 입금완료 69건 중 입금확인 문자는 4건. 웹훅 코드에는
"입금확인 문자는 PayAction 이 직접 발송하므로 여기서는 보내지 않는다"는 주석이 있었으나,
사장님 확인 결과 PayAction 은 손님에게 문자를 보내지 않는다.

→ 고침: 웹훅이 입금을 '처음' 확인한 건(`changed=true`)에 입금확인 안내를 보낸다.
문구는 관리자 경로와 같은 조립기(`lib/payment-confirmed-message.ts`)를 쓰고,
중복은 `sms_already_sent`(주문당 1회)로 서버가 막는다.

### ③ 연장(재구독) 구독의 발송 문자에 회차 표기가 통째로 빠졌다 — 93건
구독 슬롯은 원주문에 붙어 있고, 연장주문은 `orders.renews_slot_id` 로 그 슬롯을 가리킨다.
그런데 문자 코드는 슬롯을 `order_id` 로만 찾았다. 연장주문에서 나가는 발송은 슬롯을
못 만나 "8회 중 3번째" 같은 표기가 아예 붙지 않았다.

→ 고침: `renews_slot_id` 로도 슬롯을 찾고, 총 회차를 슬롯 기준(원주문 `block_weeks` +
`extended_weeks`)으로 세어 마이페이지·배송판과 같은 숫자가 나오게 했다.
한 주문에 요일이 둘이라 슬롯이 여러 개인 경우(1건)는 그 날짜에 배송이 놓인 슬롯을 고른다
(`pickSlotForShipDate`).

### ④ 구독 만료 안내가 절반에게만 나갔고, 종료 안내는 아예 없었다
`renewal_reminder_targets` 가 `marketing_consent = true` 인 회원만 대상으로 삼고 있었다.
활성 구독 73건 중 37건(51%)이 미동의라, 그 손님들은 구독이 끝나는 줄 모른 채 끝났다.
만료·종료 안내는 거래 정보성 문자이지 광고가 아니다.

또 '구독이 끝났습니다' 문자는 기능 자체가 없었다(예고 D-7/D-3만 존재).

→ 고침: 동의 조건 제거 + `END` 단계 신설(만료 다음날 1회, 크론이 걸러도 3일 내 보정).
마지막 회차 발송 문자에는 "(8회 중 **마지막** 8번째)"로 표기한다.

### ⑤ 크론이 보낸 문자가 관리자 문자 이력에 남지 않았다
발송 예고·만료 안내·입금 독촉은 각자 전용 원장에만 기록하고 `sms_log` 에는 남기지 않았다.
관리자 화면의 '문자 이력'은 `sms_log` 를 읽으므로, 실제로 나간 문자가 화면에는 없었다
(라벨 `ship_reminder = 발송예고` 는 이미 있는데 데이터가 들어온 적이 없다).
CS 때 "그런 문자 보낸 적 없다"고 화면이 답하게 되는 상태였다.

→ 고침: 크론 3종 모두 발송 직후 `sms_log` 에 적재한다.

### ⑥ 7월 21일(화) 출고 기록 누락 — 구독 9~10건
화요일 구독 10건이 7/14 출고 → **7/21 기록 없음** → 7/28 출고로 이어진다.
사장님 확인: 물건은 나갔고 기록만 빠졌다.

→ 보정 SQL 제공: `supabase/backfill-2026-07-21-shipments.sql`
(미리보기 → 실행 2단계. 재고 차감 표시를 겸하는 테이블이라 재고 주의사항을 파일에 적어 뒀다.)

### ⑦ 미입금 독촉 문자 폐지 (사장님 결정)
손님에게 나가던 자동 독촉(D1·D2)을 없앴다. 입금자명이 다르거나 이미 입금한 손님에게
기계가 독촉을 보내면 그 자체가 클레임이 된다 — 실제로 안내 문자를 한 통도 못 받은
비회원이 독촉부터 받은 사례가 있었다(SY20260829-9912).

→ 대신 관리자에게 '미입금 확인 필요' 요약 문자 한 통이 간다(하루 한 번, 여러 건이어도 한 통).
주문번호·이름·금액·경과시간이 줄 단위로 들어가고, 통장 확인 후 관리자 화면에서
[입금확인]/[취소]로 처리한다. 알림 시점은 종전 단계를 그대로 쓴다(12시간·36시간·60시간 경과).
수신처는 `ADMIN_ALERT_PHONE`.

### ⑧ 취소된 주문의 구독 슬롯이 '활성'으로 남아 있다 — 1건
SY20260813-1278 은 주문이 취소인데 슬롯은 활성이다. 배송 명단·만료 안내 대상에
계속 잡힌다. 실제로 해지된 건인지 확인 후 슬롯 상태를 맞춰야 한다(자동 수정하지 않았다).

## 2-2. PayAction 연동 점검 (2026-08 개발자문서 개정 대조)

문서를 우리 코드와 한 줄씩 맞춰 봤다.

**깨진 것 없음.** 종료 예정(DEPRECATED)으로 표시된 `POST /order-exclude` 와
`POST /cashbill-cancel` 은 우리가 쓰지 않는다. 헤더(`x-api-key`·`x-mall-id`)·Base URL·
웹훅 인증(`x-webhook-key`)·응답 규약(`{"status":"success"}`)·재전송 정책(최대 3회)은
현재 구현과 일치한다.

**보강한 것**

1. **주문취소를 PayAction 에도 알린다** (신규 API `POST /orders/{order_number}/cancel`)
   지금까지는 우리가 주문을 취소해도 PayAction 은 몰라서, 뒤늦게 입금이 들어오면
   '고아입금'이 되고 관리자에게 경고 문자가 갔다. 이제 취소 시 매칭을 끊는다
   (관리자 취소·회원 본인 취소 두 경로 모두).

2. **웹훅의 새 `cashbill` 필드를 인식한다**
   현금영수증 자동발행을 쓰는 주문에만 실려 온다. 발행 실패(`issue_failed`)면 코드·메시지를
   에러 로그로 남긴다. 우리는 아직 홈택스 수기 발행이라 지금은 오지 않는다.

**확인이 필요한 것 — 입금확인 알림톡이 두 번 갈 수 있다**

문서: *"주문자에게 결제완료(입금확인) 알림 메시지 발송을 원하는 경우에는 주문자 전화번호 및
주문자 이메일 필드를 포함하여 요청해야 합니다."*

우리는 주문 등록 시 `orderer_phone_number` 를 **이미 넣고 있다**. 즉 PayAction 대시보드의
구매자 알림이 켜져 있으면 손님은 이미 결제완료 알림톡을 받고 있을 수 있다.
(우리 `sms_log` 에는 PayAction 발송이 남지 않으므로 "65건 미수신"은 정확히는
'우리 시스템에서 보낸 기록이 없다'는 뜻이다.)

→ 대시보드 > 설정에서 구매자 알림 상태를 확인해 주세요.
   이미 나가고 있다면 `PAYACTION_CONFIRM_SMS=off` 환경변수로 우리 발송만 즉시 끌 수 있다
   (배포 불필요). 반대면 그대로 두면 된다.

**나중에 검토할 것**

- **현금영수증 자동발행**(`POST /cashbills`): 지금은 홈택스에서 손으로 발행한다.
  우리는 이미 면세(우유)·과세(요거트) 분리를 정확히 계산하므로(`lib/cash-receipt-tax.ts`)
  주문 등록에 `tax_free_amount` 를 실어 보내면 자동발행으로 넘어갈 수 있다. 별건.
- **페이위젯**: 주문 완료 화면에 입금 안내 창을 띄우고 입금이 잡히면 화면이 스스로 바뀐다.
  비회원 안내에 특히 쓸모가 있다(스크립트 한 줄 + `mallId`·`orderNumber`). 별건.

## 3. 고치지 않고 남긴 것

| 항목 | 이유 |
|---|---|
| 비회원 **선물** 주문의 주문자 안내 | 주문자 연락처를 받는 칸이 없다(받는 분 번호만 저장). 폼 변경이 필요해 별건. |
| 방문수령 구독의 '수령하세요' 안내 | 택배 발송이 없어 문자 경로 자체가 없다. 필요 여부부터 결정 필요. |
| 예정일 대비 실제 출고일 차이(8/18 예정 → 8/17 출고 등) | 운영상 앞당겨 보낸 것으로 보인다. 화면은 예정일을 보여주므로 손님이 보는 날짜와 실제가 하루 어긋난다. 규칙을 정하면 반영. |

## 4. 재발 방지

`supabase/audit-notify-consistency.sql` — 이번 점검에서 손으로 돌린 검사를 한 파일에 묶었다.
Supabase SQL Editor 에 붙여넣고 실행하면 8개 항목의 건수가 한 표로 나온다. 전부 읽기 전용.
주 1회 돌려 0이 아닌 항목만 파고들면 된다.

점검 항목: ① 주문접수 문자 없음 ② 입금확인 문자 없음 ③ 출고했는데 발송안내 없음
④ 발송 실패 ⑤ 지난 배송 문자(출고 8일 이상) ⑥ 예정일 지났는데 출고기록 없음
⑦ 주문 취소인데 슬롯 활성 ⑧ 구독 발송문자에 회차 표기 없음
